# チュートリアル: スコーピング編

「どのようにスコープを切るべきか？」という問いに、本方法論の範囲で答える。

## 先に答え

- モールドが書ける大きさになるまで切る。切れたかどうかは、モールドが書けるかで判定する
- 書ける・書けないの判定は、切る側ではなく、会ったこともないファウンドリの最大公約数を基準にする
- 切り方が良かったかどうかは、発送後のログで判定し、次のモールドから直す

本方法論は、どこで切れば正解かという切り方そのもの(ハウ)は提供しない。提供するのは、切った結果を確かめる判定と、切り方を直すための記録である。このチュートリアルは、その判定と記録を使って切り方を自分で組み立てる一周を通す。

## 前提

- 参照: `concept.md`, `lifecycle.md`, `manuals/fabless.md`, `templates/mold.md`, `templates/structs.md`, `faq.md`
- 要求がある程度言葉になった状態から始める。未整形の要求を整える手順は本方法論の範囲外とする

## 題材

経費精算システムについて、依頼者から次の要求が届いた。

1. 社員が経費を申請できる。金額、利用日、費目、領収書の有無を入力する
2. 金額によって承認者が変わる。5万円以下は上長、5万円を超えたら部長、30万円を超えたら役員が承認する。部長本人の申請は役員が承認する
3. 承認者に通知が届く
4. 不正な申請を防ぐ
5. 画面は使いやすくする

## 手順 1: 一つのモールドとして書いてみる

まず切らずに、要求全体を一つのモールドとして `templates/mold.md` に書き始める。書き切ることが目的ではない。どこで手が止まるかを見るために書く。

手が止まった箇所を、そのまま書き出す。

| 箇所 | 止まった理由 |
|---|---|
| テストデータ | 申請内容、申請者の役職、承認者の在籍状況、通知先のアドレスなど、性質の違う値が並び、項目が多くなる |
| 期待結果 | 「受付」「承認者は部長」「通知が届く」が一件のテストケースに同居し、どれで満たしたと判定するかが決まらない |
| 期待結果 | 要求 4「不正を防ぐ」に、満たしたか満たしていないかを決められる期待結果が書けない |
| 期待結果 | 要求 5「使いやすく」に、同上 |
| テストケース | 金額の境界、費目、役職、領収書の有無を掛け合わせると件数が数百件に増える |
| テストデータ | 役員本人が申請した場合の承認者が、要求に書かれていない |

## 手順 2: 止まった理由から切り口を決める

止まった理由ごとに、切り口が一つ決まる。

### 期待結果の種類が違うところで切る

「受付か却下か」「承認者区分は何か」「通知が届いたか」は、判定の仕方がそれぞれ違う。一件のテストケースに同居させず、別のモールドに分ける。

- 申請内容の受付判定(要求 1)
- 承認者区分の判定(要求 2)
- 通知の送信(要求 3)

### 外部の状態はテストデータにする

承認者区分が決まっても、具体的に誰が承認するかは組織の情報に依存する。組織の情報をモールドの中で扱うと、ファウンドリはモールドの外を調べないと作れなくなる。

承認者区分の判定は区分だけを返すところまでとし、区分から人を引く処理は別のモールドにする。そのモールドでは、組織の情報から得た値をテストデータとして受け取る形に書く。

### 書けないものはモールドにしない

要求 4 と 5 は、この時点では期待結果が書けない。`faq.md` のとおり、書けないものは仕様化されていないとして、モールドを確定しない。

- 要求 4: 依頼者に「不正」とは何かを列挙してもらう。「同じ領収書で二度申請する」のように列挙できたものから、テストケースにして新しいモールドにする
- 要求 5: 期待結果を書ける形に分解できなければ、適用範囲外として別の作法で扱う

### 決まっていない判断は外に出す

役員本人が申請した場合の承認者は、要求に書かれていない。テストケースを書くためにファブレスが推測で埋めない。

- 承認者区分のモールドでは、役員の申請を `error` とするテストケースだけを置き、承認者は決めない
- 依頼者に確認し、決まったら参照付きの新しいモールドとして出す

### 組み合わせが爆発するところで切る

申請内容の受付判定と承認者区分の判定を分けると、金額の境界と役職の組み合わせは承認者区分のモールドだけに残る。費目と領収書の組み合わせは受付判定のモールドだけに残る。掛け算だった件数が足し算になる。

## 手順 3: 切ったスコープをモールドとして書く

ここでは承認者区分の判定を書く。`manuals/fabless.md` の 1-1 から 1-3 に沿う。

### 識別

- モールドID: `tutorial-scoping-02`
- リビジョン: 1
- 発行日: 記入する
- 期限: 記入する
- ファブレス: 自分
- ファウンドリ: 相手

### テストケース

| ID | シナリオ | 事前条件 | テストデータ | 期待結果 |
|---|---|---|---|---|
| TC-001 | 下限 | なし | `{amount: 1, applicant_grade: "一般"}` | `上長` |
| TC-002 | 上長の上限 | なし | `{amount: 50000, applicant_grade: "一般"}` | `上長` |
| TC-003 | 部長の下限 | なし | `{amount: 50001, applicant_grade: "一般"}` | `部長` |
| TC-004 | 部長の上限 | なし | `{amount: 300000, applicant_grade: "一般"}` | `部長` |
| TC-005 | 役員の下限 | なし | `{amount: 300001, applicant_grade: "一般"}` | `役員` |
| TC-006 | 上限 | なし | `{amount: 1000000, applicant_grade: "一般"}` | `役員` |
| TC-007 | 課長の申請 | なし | `{amount: 50000, applicant_grade: "課長"}` | `上長` |
| TC-008 | 部長の申請、少額 | なし | `{amount: 1, applicant_grade: "部長"}` | `役員` |
| TC-009 | 部長の申請、部長の範囲内 | なし | `{amount: 300000, applicant_grade: "部長"}` | `役員` |
| TC-010 | amount が下限未満 | なし | `{amount: 0, applicant_grade: "一般"}` | `error` |
| TC-011 | amount が上限超過 | なし | `{amount: 1000001, applicant_grade: "一般"}` | `error` |
| TC-012 | 役員の申請 | なし | `{amount: 1, applicant_grade: "役員"}` | `error` |

TC-012 は、役員本人の申請を「決まっていない判断」として外に出した結果である。決まったら新しいモールドで扱う。

### 参照

- `tutorial-scoping-01`(申請内容の受付判定)

受付判定 `tutorial-scoping-01` と通知の送信 `tutorial-scoping-03` も、同じ要領で別に書く。三つを一度に書き切る必要はない。書けたものから順に発送してよい。

## 手順 4: 製造側の認識範囲で確かめる

書いたモールドを、発送する前に次の観点で読み直す。基準は自分ではなく、会ったこともないファウンドリである。

- モールドだけで作れるか。社内用語、業務の慣習、口頭で伝えた前提など、モールドの外の知識が要る箇所がないか
- テストケースに現れる語が、モールドの中で閉じているか。たとえば `上長` は、このモールドでは出力の区分名として使うだけで、誰を指すかは決めない。それが読み取れるか
- テストデータの項目数とテストケースの件数が、一度に読み切れる量か

一つでも引っかかれば、手順 2 に戻って切り直す。閾値をいくつにするかは本方法論では決めない。後の手順 5 のログを見て、自分たちの値を決める。

## 手順 5: 発送後のログで切り方を評価する

発送して一周を終えたら、次のログを見る。それぞれが、切り方のどこに問題があったかを示す。

| 見るもの | 記録 | 切り方について示すこと |
|---|---|---|
| 不備返送 | DecisionLog の RejectDecision | テストケースの書き方が足りない。切り方より書き方の問題であることが多い |
| 同じモールドへの質問 | RoutingLog | モールドに書けていない判断が、境界の内側に残っている |
| 宛先不明 | RoutingLog | 誰も決めていない判断がスコープに入っている。手順 2 の「決まっていない判断は外に出す」が漏れている |
| モールド側に原因がある差し戻し | DecisionLog の SendBackDecision | 期待結果が判定できる形になっていない。切り方かテストケースの書き方に手を入れる |
| 参照付きの追加発注 | Mold の参照 | 最初に切った時点で見えていなかった要求がある |
| 補足したくなった内容 | `tutorials/fabless-with-team.md` の手順 2 で控えたもの | モールドの外の知識に頼っている |

アンドンコールは作業環境の停止要因であり、切り方の評価には使わない。

各項目には `templates/structs.md` の Threshold を置いてよい。たとえば「モールドあたりの質問件数」に閾値を置けば、切り方が大きすぎたモールドがアラートとして浮かぶ。

## 手順 6: 切り方を直す

- 進行中のモールドは書き換えない。直した切り方は、次に書くモールドから反映する
- 漏れていた要求は、元のモールドを参照する新しいモールドとして出す
- 手順 5 で見つかった傾向を、自分たちの切り方の手がかりとして残す。「金額と役職のように、組み合わせで出力が変わる値は同じモールドに入れ、その他は分ける」のような形で書く

この手がかりの蓄積が、本方法論が提供しない切り方そのものの代わりになる。

## つまずきやすい点

**全体を先に切りきろうとする。** すべてを切り終えてから発送する必要はない。書けたモールドから順に出し、そのログを次の切り方に使う。

**書けない部分を曖昧な期待結果でごまかす。** 「適切に処理する」と書けばモールドの形にはなるが、受入完了で判定できない。書けない部分はモールドにせず、外に出す。

**決まっていない判断をファブレスが推測で埋める。** 推測で書いたテストケースは、依頼者の判断と食い違ったときに追加発注か取り下げを生む。テストケースにせず、決まってから出す。

**細かく切りすぎる。** モールド間の依存が増える。並列モールド間の依存の扱いは、現時点で本方法論の範囲外である。外部の状態をテストデータとして受け取る形にして、各モールドが単独で読める大きさで止める。

**自分が読めるかで判断する。** 切った本人は、モールドの外の前提を知っているので読めてしまう。会ったこともないファウンドリが読めるかで判断する。
