## 手順 2: 製造

モールドだけを見てソースコードを作る。以下は Python 例。

```python
def f(items: list[int]) -> int:
    return sum(items)
```

空配列に対して `sum` は 0 を返すので、TC-001 の分岐を別に書く必要はない。

モールドに書かれていない挙動を足さない。たとえば「配列が長すぎたら例外を投げる」といった処理は、テストケースに書かれていないので、実装しない。

## 手順 4: Logic Proof

```python
def test_tc_001():
    assert f([]) == 0

def test_tc_002():
    assert f([1]) == 1

def test_tc_003():
    assert f([1, 2, 3]) == 6

def test_tc_004():
    assert f([10000, 10000]) == 20000

def test_tc_005():
    assert f([0, 5]) == 5

def test_tc_006():
    assert f([1] * 1000) == 1000
```

テストケース一件につきテスト関数を一つ作る。Requirement Proof の応答と一対一で対応する。

実行し、全件 pass することを確認する。実行環境、実行結果、実行日時を残す。

## 手順 5: 納品

次の三点を揃えて ShipDecision を出す。

- ソースコード
- Requirement Proof
- Logic Proof

出荷した時点で、このモールドについての責任は終わる。

## つまずきやすい点

**モールドにない入力への対応を書きたくなる。** テストケースより長い配列、型が違う入力への対応はモールドにない。書かない。必要なら質問として出す。

**テストを Requirement Proof の根拠にしたくなる。** 根拠にはソースコードのどこで満たしているかを書く。テストが pass することは Logic Proof が示す。

**複数のテストケースを一つのテスト関数にまとめたくなる。** まとめると、どのテストケースが落ちたかが実行結果から読めない。一件ずつ分ける。
